# Desktop v2 Studio 设计

状态：设计提案，尚未实现。日期：2026-09-04。代码核对基线：`28a9d7b7`。

首期按「一个用户 + 多个 Agent」的持久群聊设计。真人多人协作、远程在线状态和多主机执行不属于首期。

## 1. 核心决定

Studio 是一个拥有成员、共享文件和公开聊天记录的协作空间。用户可以在同一个群中让不同 Agent 讨论、分工和交付，也可以随时指定某个成员。

| 对象 | 负责什么 | 与其他对象的关系 |
| --- | --- | --- |
| Project | 已登记的文件目录及其工作范围 | 一个 Project 可被多个 Studio 关联，也保留原有普通会话 |
| Studio | 成员、群消息、协作请求、共享产物 | 首期可关联零个或一个 Project；始终有自己的共享空间 |
| Session | 一个 Agent 的对话上下文与执行历史 | 每个 Studio 成员有独立 Session；群聊记录单独保存 |
| Run | Agent 对一次输入的执行 | 关联群消息、协作请求与实际执行状态 |

一个 Studio 可以跨多次用户提问长期存在。首期只有一条群消息时间线，不额外增加频道、话题、会议等层级。

导航采用上一轮的「Studio 独立分区」方案。Project 内可以显示关联 Studio 的快捷入口；入口指向同一个 Studio，不复制群聊或 Session。

## 2. 群聊的工作空间是什么

**有群聊自己的共享空间，但群空间、项目目录、Agent 执行目录需要分别定义。** 共享空间用于交换资料和结果，项目目录用于项目工作，执行目录用于某个 Agent 的临时操作。

### 2.1 文件与运行状态分开存放

以下为建议的逻辑目录，实际根目录由 Desktop 配置解析，不硬编码用户路径：

```text
<studio_workspace_root>/<studio_id>/
  shared/
    inputs/                         用户上传的材料
    artifacts/<artifact_id>/        已发布的交付物及版本
  members/<membership_id>/
    work/                           成员持续使用的草稿目录
    runs/<run_id>/                   本轮临时文件

<runtime_data_root>/studios/<studio_id>/
  元数据、成员关系、群消息、派发记录、事件游标
  成员与 Session 的映射

<registered_project_path>/          可选的外部项目目录
```

数据库布局不是本提案指定的实现；第二部分表示宿主管理的数据范围，不能作为群共享目录暴露给工具。

### 2.2 没有关联 Project

- 创建 Studio 时分配稳定的 `studio_id` 和群共享空间。
- 每个成员默认在自己的 `members/<membership_id>/work` 执行。
- 成员通过文件引用读取群资料，通过发布产物把草稿变成其他成员可见的版本。
- UI 的文件入口默认打开「群文件」，用户无需先创建 Project。
- 群成员共享已发布资料，不自动共享彼此完整的 Session、模型上下文或临时日志。

### 2.3 关联了 Project

- Studio 的共享空间继续存在，Project 作为额外工作范围绑定；不把整个群目录塞进项目仓库。
- 右侧文件面板区分「群文件」与项目名称，例如「Sage」。
- 讨论、研究成员仍使用成员工作目录；需要修改项目的执行 Run 才以项目目录作为工作目录。
- 项目权限沿用用户已有授权，再按成员能力收窄。加入 Studio 本身不扩大工具或文件权限。
- 项目文件引用保存项目身份和相对路径；交付物引用保存 `artifact_id + version`，避免把作者机器的绝对路径直接交给其他成员。
- 后加 Project 不移动已有群文件。更换或解除关联只在相关 Run 停止后生效；已有 Run 使用启动时冻结的工作空间版本，不能执行到一半换目录。

### 2.4 谁能写共享内容

首期采用「私有草稿 + 发布版本 + 项目单写者」：

1. 每个成员写自己的草稿目录。这里的“私有”首先是用途和授权边界，目录分开本身不等于安全隔离。
2. 上传材料作为本次输入的稳定版本；修改后产生新版本。
3. 成员发布交付物时，宿主校验来源路径、冻结内容并生成版本引用。其他成员读取已发布版本。
4. 修改项目的 Run 必须取得项目写入权；其他并发成员读取已知版本或快照，不能同时改同一项目。
5. 项目写入权以规范化后的项目根目录为范围，覆盖访问该目录的 Studio 和普通 Session。若未能接入所有写入口，首期限制为串行执行项目写任务，不能宣称已解决跨会话写冲突。
6. Shell、脚本等写入也必须受同一执行绑定约束，不能仅在文件编辑工具上加锁。外部编辑器修改通过版本/内容校验检测冲突，不自动覆盖。

宿主必须验证实际文件、进程权限。只在提示词里写“请勿访问其他目录”不构成隔离；Provider 不能满足策略时，应拒绝对应执行，或明确降级为受信任本机协作，不伪装成安全沙箱。

群归档停止自动派发，保留成员、消息和文件。移除成员不删除其已发布结果。删除群不能连带删除关联 Project；群文件的清理与聊天归档分别处理。

## 3. Agent 怎么知道该 @ 谁

**靠成员能力目录、明确的协作规则和结构化工具。模型负责选择合作对象，宿主负责身份、授权与送达。**

### 3.1 每次执行注入的 Studio 上下文

由新的 `StudioContextProvider` 生成：

- 当前 Studio、自己的 `membership_id`、角色与本轮任务。
- 当前成员名单：稳定 ID、显示名、职责、能力、是否仍可接收请求。
- 群的目标、用户约束、相关决策与共享资料引用。
- 当前触发消息、引用的上下文、尚未完成的依赖和预期输出。
- 发言与请求规则，以及剩余的请求深度、次数和预算。

同一个 Agent 模板加入两个 Studio，要产生不同的 `membership_id` 和独立 Session。请求目标使用成员身份，而不是全局 Agent 名称；重名、改名不会误投递。

名单由宿主从成员配置生成，职责和能力来自真实 Agent 配置。模型可以读取成员当前任务摘要，但运行状态只是快照，调度器会在真正派发时重新检查。

提示词示意：

```text
你是 Studio「产品讨论组」的 Designer，成员 ID 为 member_designer。

成员：
- member_sage / Sage：协调目标、拆分任务、合并结果。
- member_designer / Designer：交互流程、页面结构、视觉设计。
- member_engineer / Engineer：代码实现、技术可行性、测试。

自己能完成的工作直接完成。
当问题需要其他成员的能力或产物时，向对应成员发出具体请求。
请求包含目标、必要上下文、预期输出和相关文件引用。
只有需要对方行动时才使用 request；引用名字或告知结果使用 note。
不要猜测成员 ID，也不要因为别人发了结果就自动回复。
正文中的 @ 只用于展示；实际请求必须调用 studio_send_message。
收到任务结果后继续原任务，避免再次请求同一份结果。
```

这些是 Studio 模式下新增的契约，不覆盖现有普通委派模式的叶子 Agent 限制。

### 3.2 一个典型判断

Designer 在设计输入框时不确定现有附件协议是否支持多文件，成员目录说明 Engineer 负责代码与协议。Designer 因此请求 Engineer 核实；Engineer 返回支持范围和源码证据；Designer 再完成设计。

这不需要每个 Agent 阅读群中每一句话后都发言。没有被直接请求的成员可以保持空闲。

首期提供「按需响应」默认策略：用户未指定成员时先交给协调者，用户明确 @ 某成员时直接交给该成员。协调者是一个普通成员，其结果合并职责由角色配置定义；消息投递本身由确定性的服务执行，不依赖协调者一直占用模型运行。

## 4. @ 的交互与协议

### 4.1 用户输入

输入 `@` 后显示群成员选择器，选中后生成绑定 `membership_id` 的 mention token。原始文本和 token 一起保存。手动键入但未解析成功的名称保持普通文字，不静默变成请求。

用户提交时，明确选中的 @ 成员默认是本轮接收者；输入框显示接收对象。引用历史消息中的 @、代码块中的 @ 和转发内容中的 @ 不产生新的接收者。

### 4.2 Agent 工具

新增 `studio_send_message`，示例为接口提案：

```json
{
  "intent": "request",
  "recipient_member_ids": ["member_engineer"],
  "text": "@Engineer 请核实现有附件协议是否支持多文件，并给出实现位置。",
  "reply_to_message_id": "msg_user_42",
  "expected_output": "支持范围、限制、源码引用",
  "context_refs": ["message:msg_user_42", "artifact:design_draft:v2"]
}
```

| intent | 用户看到什么 | 是否启动执行 |
| --- | --- | --- |
| `note` | 一条普通发言，可展示提及的人 | 不启动其他 Agent |
| `request` | 指向某人的问题或协作请求 | 为每个目标生成一条受预算约束的派发 |
| `result` | 对某条请求的回答、产物或结论 | 只满足对应依赖；必要时恢复原请求者，不广播唤醒 |

`result` 必须包含有效的 `request_id`，后端验证当前成员确实负责该请求。运行完成另有执行状态事件，不能只靠一句“完成了”结清依赖。无有效结果的完成应标为“未交付”，由请求者决定下一步。

`sender_member_id`、Studio 身份、权限、根请求 ID、因果链和去重键由宿主从实际工具调用推导，不接受模型自行声明。Agent 只能请求仍在本群且对当前操作有权限的成员。

工具成功返回的是已持久化的 `message_id`、`request_id`、派发状态，不表示对方已经完成。请求应同时得到「消息 + 待派发事件」的原子记录；重试同一工具调用返回同一记录。

### 4.3 为什么不能用正则扫描 @ 触发

正文里可能存在示例、引用、同名成员，流式输出也可能重放。基于文本匹配会误派发、重复派发，甚至把外部文件中的文字当成任务指令。

因此：**mention 负责展示和引用，request 负责动作，result 负责依赖完成。** Agent 只在文字中写 `@Engineer` 而未调用工具时，不会实际唤醒 Engineer。

### 4.4 调度与防循环

- 群消息服务先保存公开消息，调度器再派发到目标成员的收件箱。
- 同一成员 Session 同时最多一个活动 Run；后来的请求排队，UI 显示排队原因。新用户指令可以通过既有中断机制调整当前任务。
- 首期建议最多三个成员同时执行；项目写任务另外受写入权限制。
- 需要等待其他成员时，持久化依赖和恢复点，让出执行资源；不让 Shell、模型连接或父 Run 同步阻塞等待整个协作链。
- 调度器检查阻塞依赖图。例如 A 等 B，而 B 又请求正在等待自己的 A，拒绝建立循环，向 B 返回明确原因；返回结果的反向消息不算新任务依赖。
- 同一根请求建议最多八次协作派发、最多三层依赖，并共用时长和费用预算。具体默认值在交互测试后调整。
- 首期 Agent 不能主动请求自己，不能发 `@所有人` 触发全员运行。协调者可以显式选多个成员拆分任务。
- 达到上限、目标被移除、依赖失败时产生可见阻塞状态，不无限重试。既有成员配置决定是否允许接收新请求。
- 停止一条根请求时停止其后续派发并取消所属活动执行；已完成结果保留。停止整个 Studio 才影响该群的所有根请求。

### 4.5 返回结果不会引发“互相感谢”循环

Engineer 的结果消息关联 Designer 发起的请求。调度器只唤醒仍等待这一结果的 Designer，且只恢复一次；其他成员不会因结果文本或 @ 显示被唤醒。Designer 合并结果后完成原任务，协调者只在本轮确实需要汇总时执行一次。

独立的新用户请求拥有新的因果链，不能被旧任务的迟到结果覆盖。迟到结果仍可保留并标明原请求，不能静默应用到新任务。

## 5. Session、上下文与恢复

### 5.1 群历史不是所有 Agent 共用的一条模型历史

```text
Studio
├─ 公共消息时间线与决策摘要
├─ Sage 成员 Session
├─ Designer 成员 Session
├─ Engineer 成员 Session
├─ 请求、依赖、投递记录
└─ 工作空间与产物索引
```

每个成员保留自己的工具调用、执行检查点与模型续接数据。调用另一个成员时注入必要的任务上下文和明确引用；不把请求者的完整模型历史复制给接收者，不把其他人的工具结果拼进自己的 provider continuation。

上下文使用“稳定角色与名单 + 群决策摘要 + 相关消息 + 当前任务”的组合。成员可以通过受权限控制的 `studio_read_messages` 和产物读取工具获取更多信息。读取群历史不会主动触发 Agent。

用户从普通 Session 创建 Studio 时，显式选择要带入的消息和文件，形成可追溯的上下文副本；原 Session 保留。首期可先不提供此快捷功能。

### 5.2 新增的数据关系

| 记录 | 必要字段 |
| --- | --- |
| Studio | ID、owner、名称、可选 Project、工作空间配置版本、调度策略、归档状态 |
| StudioMember | membership ID、Agent 模板 ID 与配置版本、角色、Session 映射、入退群状态 |
| StudioMessage | ID、单调序号、发送者、正文、结构化提及、intent、reply_to、产物引用、源 Run |
| StudioRequest | 根请求、发起者、目标、原消息、预期输出、依赖、状态、预算 |
| StudioDelivery | 请求、目标、幂等键、投递/消费状态、实际 Session/Run、重试记录 |
| StudioArtifact | ID、版本、发布者、来源 Run、内容摘要/哈希、文件范围 |

群消息是公开交流的事实来源；Session 是执行历史的事实来源。通过源 Run、消息和请求 ID 关联，两者不互相冒充。

### 5.3 恢复要求

1. 群消息和派发意图在同一个持久化事务内提交，或使用具有同等保证的原子存储操作；不采用“先显示消息，后尽力发任务”。
2. 调度允许至少一次投递，消费者按目标和请求去重；创建 Run 使用稳定幂等键。
3. 消费、Run 绑定、结果发布都能在重启后对账。若 Run 已完成但群结果尚未发布，只补公开结果，不重跑工作。
4. 成员 Session 的串行约束由持久化调度保证；不能仅依赖当前进程中的字典和锁。
5. 用户输入、审批、等待成员、等待项目写入权分别保存原因。前端重连后由快照重建，不推测状态。
6. 已越过副作用边界但结果未知的操作进入“待核对”，先 reconcile，再决定恢复；消息去重不等于外部副作用恰好一次。
7. 首期只承诺单机恢复语义；多主机分布式部署需要额外的持久化 claim、fencing、事件订阅和 Provider 能力验证。

## 6. 群聊显示什么

**主区隐藏默认执行过程，保留公开交流和交付结果。** 如果只剩最后答案，用户会不知道任务交给了谁、为什么停住，也无法在关键问题上介入。

| 内容 | 主聊天区 | Studio 详情 |
| --- | --- | --- |
| 用户消息、成员明确发出的讨论/提问 | 展示 | 可定位到相关成员 |
| 成员之间的请求与交接 | 展示一条简洁消息 | 展示请求状态与依赖 |
| 成员答案、结论、文件交付 | 展示 | 可查看来源与关联执行 |
| 搜索、读文件、Shell、重试等工具过程 | 默认不展示 | 按成员/Run 展开 |
| 一般运行进度 | 群标题处显示“2 位成员执行中” | 展示各成员状态 |
| 需要用户决策、审批、失败、待核对 | 必须有可见入口 | 展示原因和处理动作 |
| 模型私有推理或内部协议状态 | 不展示 | 不作为“执行过程”展示；仅保留允许的诊断元数据 |

公开消息通过 `studio_send_message` 明确发布；普通工具输出和内部过程消息不自动转成群发言。成员最终回答可通过结果适配器发布为群结果，与工具显式发布的结果共享唯一发布键，避免出现两份相同回答。

公开答案允许流式更新同一个消息 ID；在完成前显示生成状态，重连后继续更新。错误或取消不能留下一个看似已完成的交付物。工具 stdout 不能混入公开答案流。

用户可以在群里继续 @ 或补充要求，点击一条请求/结果打开右侧对应成员和执行。关闭右侧面板不停止后台任务，也不能让待处理审批失去入口。

## 7. 右侧 Studio 详情

采用现有右侧 Workspace Panel/Dock 的扩展方式，增加 `StudioDetailsPanel`。Studio 详情、文件、终端共用右侧区域，不为群聊再造一套固定窗口。

默认详情先展示成员列表；点击成员进入该成员的当前执行，保留返回列表入口。详情可以关闭，选中另一群时必须更新所属 Studio，不能残留前一个群的运行状态。

```text
┌────────────────┬──────────────────────────────────┬───────────────────────────┐
│ Sage           │ 产品讨论组             [详情]    │ Studio 详情      文件  × │
│                │ Sage · 2 位成员执行中            │                           │
│ Studio         ├──────────────────────────────────┤ 成员                      │
│  产品讨论组    │ 你：讨论附件交互的实现方案       │ Sage       等待成员       │
│  灵感碰撞      │                                  │ Designer   等待 Engineer  │
│                │ Designer：@Engineer 请核实协议   │ Engineer   执行中         │
│ 项目           │                                  │                           │
│  Sage          │ Engineer：支持多文件，限制是…    │ Engineer                  │
│   优化工具展示 │                                  │ 当前任务  核实附件协议    │
│                │ Designer：方案已更新             │ 来自      Designer        │
│ 最近           │ [附件交互方案.md]                │ 已运行    00:38           │
│  本周计划      │                                  │ [停止] [@ Engineer]       │
│                │                                  │ ▸ 执行记录                │
│                │                                  │ 产物                      │
│ 设置           │ [发消息，@ 指定成员          ↑]  │ 附件协议说明.md           │
└────────────────┴──────────────────────────────────┴───────────────────────────┘
```

这些是功能标签和实际任务内容，不在 UI 额外增加副标题、解释段落或字段说明。

### 7.1 成员状态

| 状态 | 由什么决定 | 可用动作 |
| --- | --- | --- |
| 空闲 | 没有未结请求或活动 Run | @ 成员 |
| 排队中 | 有请求，但并发/成员/项目资源未满足 | 取消该请求 |
| 执行中 | 实际 Run 正在执行 | 停止、查看执行记录 |
| 等待成员 | 有未满足的成员依赖 | 查看正在等待的请求、停止 |
| 等待你处理 | 存在待答复问题或审批 | 回答、审批/拒绝 |
| 已完成 | 最近请求已交付，当前无新任务 | 查看结果、继续 @ |
| 失败 / 待核对 / 已停止 | 实际失败、未知副作用、取消记录 | 查看原因；符合恢复条件时继续 |

不使用“在线”表示 Agent 状态，也不猜测完成百分比。队列/依赖状态是 Studio 调度状态，Run 状态是运行时状态，两者联合形成展示状态，不直接塞进现有 `RunStatus` 枚举。

成员详情可查看当前任务、请求来源、等待对象、已运行时长、结果、产物和执行记录。Token/费用只展示运行时已有数据，不从文本估算。高级诊断放在展开区域。

执行记录复用已有 Process Panel 的工具分类和连续分组规则，但定位到该成员的 Run。切换成员只改变详情选择，不切换主区群历史。

### 7.2 视觉与操作规则

- 前端落地使用 `liquid_glass_widgets` 的 `Glass*` 组件实现侧栏、输入框、详情容器及适合的菜单；延续现有克制的玻璃效果。
- 正文优先可读性，使用深浅色成对的颜色；不靠颜色单独表达成员或状态。
- 成员名、用户文字、模型名、文件名保留原样；UI 自有标签适配现有多语言。
- 普通消息动作使用低干扰图标，提供 Tooltip、语义标签、键盘焦点与反馈。
- 窄窗口时详情通过现有紧凑布局打开；始终保留群聊天入口和待处理操作入口。

## 9. 首期范围与验收

首期固定成员名单，由用户创建群并选择成员；指定一个协调者，默认按需响应。提供群共享目录、可选单 Project、公开群消息、成员 @ 请求、结果回流及右侧详情。暂不做自动拉人、自由全员连续讨论、多个项目并写、真人多人权限和分布式运行。

建议按三步交付，每步保留可验证的边界：

1. 群数据、文件、成员 Session、用户 @ 与右侧详情；打通单成员执行和真实状态。
2. Agent 发 request/result、依赖等待与恢复、上下文投影和预算约束；打通成员互相协作。
3. 项目写协调、重启恢复、失败核对、UI 深浅色与多语言验证；达到首期完整使用条件。

关键验收场景：

- 无 Project 的群可以上传资料、让两个成员协作并读取对方已发布的产物；不同 Studio 的 Session/文件不串用。
- 同一 Agent 加入两个群、成员改名或重名，@ 始终投递到正确的成员身份。
- 用户 @ Engineer 只触发 Engineer；用户无 @ 时只先触发协调者；普通 note 和引用中的 @ 不触发执行。
- Designer 请求 Engineer 后让出执行资源；Engineer 返回结果后 Designer 仅恢复一次，其他成员不被唤醒。
- 重复工具调用、断线重连、完成后发布前重启均不重复派发或重复展示结果。
- 依赖环、预算耗尽、成员退出和迟到结果产生明确状态，没有无限循环或悬空等待。
- 单个成员停止、根请求停止、全群停止影响范围正确；关闭详情面板不停止任务。
- 等待用户审批在详情关闭后仍可发现和处理；正文只隐藏工具过程，不隐藏失败和待处理事项。
- 多个 Studio 与普通会话访问同一 Project 时，写入冲突被串行化或明确阻止；外部改动不会被静默覆盖。
- 日志证明真实 workspace binding、Session 和 Run 身份正确；不会把仅目录分离宣称为安全隔离。
- 深浅色、窄窗口、键盘 @ 选择、成员详情切换、文件引用、错误恢复均能完成真实操作。

首期的完成标准是：用户能看懂谁在做什么，成员知道何时请求谁，协作可以恢复，群结果能追溯到实际执行和文件版本。
