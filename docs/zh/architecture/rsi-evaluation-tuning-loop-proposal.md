## 1. 目标与已确认原则

本次改进的首要目标是提高 RSI 产生有效改进的能力，并可靠判断候选是否真的变好。降低 token 消耗是次要优化，不能以减少必要证据、跳过回归或降低验证标准为代价。

已经明确的方向：

1. eval 输出可行动、可检验的诊断，而不只是全面挑错。
2. tuner 每轮围绕明确的机制假设工作，说明预期行为变化与验证方法。
3. 闭环遵循“先暴露失败，再修改，再验证”。新增训练题先测量当前保留版本。
4. 保持验证集隔离：tuner 只得到验证分数，不得到验证执行轨迹、分析、题目或答案。
5. 方案是通用优化协议，不将 TauRetail 的任务、工具、身份验证或业务规则写入框架。

其余具体协议、统计门槛和实施顺序是本稿提出的设计，需在实现前进一步确定。

## 2. 问题与设计取向

近期实验暴露的关键问题不是“没有生成改动”，而是改动依据与效果证据之间缺少稳定联系：

- 任务失败、合法但未完成的流程、模拟用户变化、环境问题和评分疑点容易混在同一分数中。
- 诊断中的一般性瑕疵可能比真正影响结果的错误更突出，引导 tuner 优化次要问题。
- 训练侧已经通过时，tuner 仍被推动修改；新增题在修改后才执行，无法事先提供失败证据。
- 修改可能将原策略没有要求的限制引入生产策略，使原本有效的路径失效。
- 新候选与保留版本历史成绩比较，容易把执行波动当作提升或退化。
- 每轮采纳、达到目标、稳定性确认和独立泛化验证是不同结论，需要分别记录。

应把权威评分、因果诊断、修改决策和版本选择分开。任何一个模型的解释或自述，都不能单独证明修复有效。

## 3. 通用角色与数据边界

| 角色/组件 | 输入与职责 | 不可越过的边界 |
|---|---|---|
| 评分组件 | 按固定评分协议计算结果，保存分项检查与依据 | 不因诊断解释而事后调整标准 |
| eval | 对执行证据进行归因，生成问题卡、成功对照和不确定性 | 不把案例答案变成生产指令，不自行改变固定分数 |
| tuner | 根据训练问题卡提出假设、编辑候选并说明预期行为 | 不读取验证/测试内容，不扩张权限或修改评分 |
| 实验编排器 | 管理训练测量、候选评测、对照执行和证据归档 | 不以缺失评分补零，不悄悄丢弃失败结果 |
| 选版组件 | 按预先定义的目标、门槛与风险约束选版 | 不把 tuner 自述、诊断置信度当作实际收益 |
| 独立验收组件 | 冻结候选后与基线进行独立测量 | 不把测试结果反馈为逐轮调优材料 |

上述是职责划分，不要求增加同等数量的模型 Agent。确定性的排序、协议校验、统计与状态管理应优先由程序完成。

没有外部评分器时，可继续使用模型评分，但必须区分“评分结果”和“解释性诊断”，固定评分提示词、模型绑定及协议，并记录其不确定性。

## 4. eval：面向因果与行动的问题卡

### 4.1 诊断顺序

1. 明确实际未满足的评分条件，区分计分条件与仅供诊断的检查项。
2. 确认执行、评分和环境记录是否有效且足以支持分析。
3. 判断在当时的信息、权限和用户授权下，是否存在可执行的更好决策。
4. 定位最早的、与失败结果有关的偏离，区分主因、促成因素和无关瑕疵。
5. 有成功执行时进行对照，寻找关键决策差异；不同结果本身不证明因果。
6. 给出可测试假设及反证；证据不足时明确保留未知。

### 4.2 问题卡字段

| 字段 | 要求 |
|---|---|
| `issue_id` | 稳定标识，关联问题簇与历史实验 |
| `failed_conditions` | 权威评分的具体失败条件及引用 |
| `attribution` | agent 可控、环境、用户模拟、评分疑点、基础设施、混合或未知 |
| `causal_status` | 已证实的可控偏离、因果假设、非因果瑕疵或证据不足 |
| `critical_decision` | 关键决策、前置条件以及实际偏离 |
| `evidence_refs` | 绑定版本、案例、trial、消息/工具索引的证据引用 |
| `successful_contrast` | 成功路径的不同决策及适用条件；没有则为空 |
| `hypothesis` | 一个可被实验支持或否定的改进假设 |
| `expected_observation` | 修复后应观察到的行为变化 |
| `counterevidence` | 不支持归因的事实、替代解释和缺失信息 |
| `protected_behaviors` | 需要保留的成功行为与政策边界 |
| `priority` | 严重规则违反、任务结果相关或一般质量问题 |

字段名称是协议草案，不要求一次性改变所有现有公共 API。

### 4.3 优先级与处理方式

- 严重权限或业务规则违反：即使任务分数通过，也应单独处理并阻止不合规候选被采纳。
- 与失败结果相关的可控错误：进入主要调优队列。
- 一般表述、效率或风格瑕疵：单独积累；只有对应优化目标或有明确实验依据时才触发修改。
- 环境、场景或评分争议：进入测量问题队列，不强迫 tuner 通过改提示词修复。

任务分数与失败归因同时保留。合法转人工但任务未完成，可以仍是任务失败；这不自动构成 agent 应当执行未授权操作的证据。

评测材料不完整时应补读或标记分析不完整。按需阅读不允许把局部片段包装成完整因果结论。

## 5. tuner：假设驱动的候选实验

### 5.1 实验卡

每个候选在执行评测前保存以下内容，防止事后根据结果改写成功标准：

- 关联问题卡和当前保留版本哈希。
- 主要机制假设与适用范围。
- 具体修改位置、修改理由，以及为什么现有规则不足以解决问题。
- 预期行为变化、预期影响的任务结果。
- 支持假设、否定假设和仍无法判断的观测条件。
- 用于验证的训练案例、同类案例和成功保护案例。
- 潜在退化、不可违反的业务规则，以及必要的资源影响说明。

一个候选围绕一个主要机制，可包含必要的配套修改。多个独立机制混在一起时，应拆分实验，或明确承认归因能力下降。

### 5.2 修改约束

1. 新增生产限制须追溯到原始政策或经过验证的必要条件，不能从个别轨迹偏好推导新业务规则。
2. 已有规则执行失败时，检查优先级冲突、流程、资源加载和能力缺口，不默认重复追加提示词。
3. 根据问题选择 instructions、skills、tools 或 procedure；只能在授权优化范围内修改。
4. 允许小范围修改，也允许有证据支持的整体重组，不强制每轮全文重写或追加补丁。
5. 对候选实际 diff 进行范围检查，核对是否存在实验卡未解释的变化。
6. 无可支持的假设时允许不修改，提出需要补充的训练测量，或报告测量问题。

### 5.3 通用示例

假设：Agent 将“使整体配置满足最优目标”误解为“所有组成项都必须改变”。

修改：区分目标配置与需要执行的变更集合，允许保留已满足目标的组成项。

预期：已有最优项保持不变，其他项按约束修改；同时不损伤用户明确要求全部更换的任务。

验证：原失败案例、不同初始状态的同类训练案例、明确要求全部改变的成功保护案例。

这只是实验卡的格式示例，不作为框架内置领域规则。

## 6. 训练与调优闭环

### 6.1 标准流程

1. 冻结本次实验的评分协议、数据集版本、模型及环境绑定。
2. 执行或补齐当前保留版本的训练测量，建立问题卡和成功保护案例。
3. 根据严重性、重复性、可控性和覆盖范围选择问题簇。
4. tuner 提交实验卡并编辑候选；没有有效假设则进入补测或暂停该问题簇。
5. 执行配置和修改范围检查。
6. 测量假设相关训练案例，检查行为是否按预期改变。
7. 执行必要的扩展训练回归，覆盖可能受影响的成功路径。
8. 候选达到进入条件后，进行独立验证集比较。
9. 记录采纳、拒绝或证据不足；更新经验，再决定下一轮工作。
10. 达到阶段目标或停止条件后冻结候选，进行独立验收。

### 6.2 新增训练题的顺序

新增训练题必须先测当前保留版本，再进入本轮调优输入。候选与保留版本应在相同的相关案例上形成可比较证据。

已测训练题全通过但验证表现不足时，优先扩大未覆盖的训练任务类型、增加必要重复或开展经审查的训练挑战，不继续强迫 tuner 改写成功轨迹。新题不能通过修改目标、答案或评分标准来制造成功。

已有失败结果必须保留。可以补测估计稳定性，但不得“重跑直到通过”并覆盖旧失败。

## 7. 验证和测试隔离

验证集继续只向 tuner 提供匿名分数及选版结果，不提供轨迹、诊断、原始题号、参考答案或可反推出题目内容的自由文本解释。

训练证据索引、经验文档、错误信息、文件路径以及跨轮摘要都必须遵守同一边界。不能通过新建问题卡或经验汇总绕过隔离。

确需将某个验证案例用于训练诊断时，应明确转入训练集、补充新的独立验证案例并创建新数据版本；不能再把已暴露案例视作未见验证证据。

区分两类测试：

- 现有逐轮、仅供人观察的 test 可以作为观察数据，但不得宣称其反复被查看后的结果仍构成独立验收。
- 证明泛化提升需要冻结最终候选后使用未参与选择的独立验收数据。人根据逐轮测试结果选版，也属于参与选择。

是否默认保留逐轮观察测试是产品配置问题，不因节省 token 就在本方案中强制取消。独立验收边界是效果可信性的要求。

## 8. 如何确认真的变好

### 8.1 三层证据

**机制改善**：实验卡预期的行为是否出现、原错误是否减少。行为指标由具体任务和观测接口提供，框架不硬编码领域判断。

**整体改善**：相关训练问题修复后，候选在独立验证比较中仍有净收益，且满足政策、回归与资源约束。

**泛化改善**：最终冻结候选在独立验收数据上，相比原始基线仍得到支持。验证改善但验收不支持时，应如实报告尚未确认泛化提升。

### 8.2 正式选版比较

- 候选与当前保留版本使用同一数据版本、评分规则、重复计划和环境条件。
- 在同一比较窗口重新测量双方，避免只拿新候选挑战旧版本历史高分。
- 运行顺序交错或平衡；环境状态在每个 trial 间隔离、重置。
- 可以固定种子时使用配对种子，但不能把种子相同当作整个交互完全确定。
- 同时报告修复案例、退化案例、任务成功率、同题稳定性和严重违规。
- 统计分析按案例成组处理重复执行，不将同题多次执行简单视作独立新样本。
- 最小有意义收益、可接受退化、硬性拒绝条件与统计方法应在实验前确定。
- 采用分阶段补测时，需预先限定补测和停止规则，不能持续窥探分数直到出现有利结果。

具体重复次数不在本稿中写死。它应由样本规模、执行波动及所需结论强度决定；预算不足只能降低结论确定性，不能降低标准后宣称有效。

### 8.3 结果状态

| 状态 | 含义 |
|---|---|
| 采纳 | 达到事先约定的收益与风险门槛，证据足够 |
| 拒绝 | 明确无效、退化或违反硬性要求 |
| 证据不足 | 结果接近波动范围、测量不足或存在未解决争议 |

另行记录是否达到业务目标、是否完成稳定性确认、是否通过独立验收。采纳不自动意味着以上三项全部成立。

## 9. 经验与证据持久化

经验库围绕机制假设组织，记录适用条件、实际修改、行为变化、任务结果、反证、退化和未解问题。

“被采纳”只说明通过了当时的选版规则，不能直接作为因果假设正确的标签。应区分假设得到支持、被否定和仍未验证。

每个实验至少保存：

- 原始基线、当前保留版本和候选版本的内容哈希及实际 diff。
- 模型、评分器、用户模拟器、数据和环境版本绑定。
- 问题卡、实验卡，以及 eval/tuner 实际收到的请求与返回。
- 目标执行、工具结果、评分明细、诊断和有效性检查。
- 选版比较的全部有效 trial、缺失/故障记录、统计方法和决策。
- 证据读取范围、截断/缺失标记及完整归档入口。

明确区分原生 session 与长期归档证据。临时工作目录清理后，不能仅凭 session ID 宣称会话完整保留；归档应足以复核关键行为与决策。

## 10. token 与效率：次要目标

优先保证效果。即使开销主要来自执行环节，也不能为了减少执行次数而省略必要的新旧对照、成功保护检查和独立验收。

可作为后续优化的措施：

- 按角色与阶段记录 token、延迟和执行次数，先确认实际成本构成。
- 对完全相同且绑定一致的证据复用诊断；对相同候选去重。
- 用问题卡和索引定位必要证据，减少重复复制完整轨迹，同时保留补读能力。
- 对已经明确违反规则或实验假设明显失败的候选提前终止，不继续执行无意义的后续测量。
- 对接近门槛、波动较大的比较增加测量；证据清晰时避免无理由重复。

旧执行缓存可用于发现问题和初步筛选，不自动替代正式选版所需的新测量。成功样本可以按风险组织诊断深度，但不能默认移除成功样本的规则检查或回归作用。

## 11. 实施阶段与验收标准

### 阶段一：诊断与假设协议

新增问题卡和实验卡，在现有归档中保存并引用；调整 eval/tuner 的职责和输出要求。

验收：能明确区分任务失败主因与一般瑕疵；证据不足不强制生成修复；候选有事前假设、反证条件和保护行为；验证材料不进入 tuner 输入。

### 阶段二：训练证据闭环

调整训练增长顺序，新增题先测当前保留版本；支持成功/失败对照、无修改、请求补测和测量问题队列。

验收：新增训练问题可以在编辑候选前提供真实失败轨迹；训练全通过时能补充覆盖；不会为了产生候选而强制修改成功策略。

### 阶段三：效果确认与选版

建立新旧版本正式比较、采纳/拒绝/证据不足状态，区分业务目标、稳定性和独立验收。

验收：不再只用保留版本历史高分选版；全部有效失败被保留；重复执行的统计处理有明确规则；只有独立验收支持时才宣称泛化提升。

### 阶段四：展示与效率完善

界面分别显示当前候选、保留版本、评测指标与证据状态；完善归档与成本报表，再优化重复工作。

验收：均值、重复成功率、选版指标与收敛指标不会混淆；用户能追溯“为何修改、为何采纳、是否真正验证”；节省成本不损害前三阶段的有效性。

## 12. 方案自身如何验证

实现后不能仅展示一次成功的优化运行。应在相同初始 package、任务数据、模型和环境绑定下比较旧流程与新流程，并覆盖多种任务类型、多次独立优化运行。

主要评价：独立验收上的净提升、产生可重复有效候选的比例、错误采纳和严重退化，以及失败归因的人工抽查质量。

同时报告资源消耗，但不以更便宜代替更有效。样本有限时明确限制结论范围。通过受控实验逐步区分问题卡、训练先测和选版复测各自的贡献，避免把所有收益归给某一个改动。

## 13. 实现前需确定的事项

1. 问题卡、实验卡与现有 diagnosis / patch / experience 字段如何兼容。
2. 正式选版的主要指标、最小有意义收益、硬性拒绝项及统计方法。
3. 重复测量、补测与停止规则，以及证据不足时的产品行为。
4. 训练问题簇和成功保护案例的选择规则。
5. 场景或评分争议的人工确认入口及数据版本迁移方式。
6. 逐轮观察测试与独立验收数据的产品区分。

以上参数尚未最终确定；本稿不构成对具体阈值、重复次数或测试默认开关的确认。
