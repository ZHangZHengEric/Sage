# SAgents V2 效率与质量检查

日期：2026-09-12。范围为当前工作区的 V2 上下文、Agent 执行与流式提交、Session Memory、内置文件存储、会话协调及 Desktop / Server 接入。检查基于代码热点分析、故障与边界回归、既有联合测试及本地合成基准，不代表生产容量认证。

## 服务器核心复查结论

后续按明确的单机并发目标继续优化，已移除租约保护对不同 Run 写入的全局串行限制，并补齐 Server 并发配置；最新结果见[单机并发说明](sagents-v2-single-host-concurrency.md)。

V2 已具备服务器 Agent 核心的主要机制：运行状态与事件一致提交、幂等准入、租约与 fencing、原子租户配额、有界执行、上下文分区及可替换基础设施端口。适合在明确的单进程写入边界和资源配置下作为并发服务器核心继续部署验收。当前内置实现还不能被认定为已经验证的大规模分布式版本；增加 HTTP worker 数不会自动获得跨进程订阅、分布式调度或共享写入安全。

第二轮重点检查故障和资源边界，并增加以下修复：

| 风险 | 处理 |
| --- | --- |
| Job 执行信号量限制了运行数，但等待任务可无限创建 | 原子限制已接纳且尚未退出的任务；满载返回可重试的 `job.queue_full`；已有幂等请求仍返回原任务 |
| 重连保护期内终态记录不能淘汰，快速短任务可持续积累 | 总记录数达到终态保留额度与接纳额度之和时拒绝新增，保留已有重连数据 |
| 运行中输出无默认上限，小块输出有额外对象开销 | 单任务及运行时整体同时限制输出字节和块数；`JobSnapshot.output_truncated` 明确报告截断 |
| 终态清理先于已注册等待者恢复，导致成功任务报 not found | 等待者与取消操作持有原任务记录，完成后返回其终态快照 |
| SQLite 调用取消后线程未结束，但实例锁提前释放 | 线程结束回调释放锁；同一事件循环所有内置记忆实例共享最多 8 个后台 I/O 名额；取消排队请求不留下锁 |
| 文件调度器写线程仍在 fsync / replace，取消允许宿主提前释放写入权 | 延迟传播取消直到写线程结束，覆盖重复取消；结果不明的持久化失败仍要求重开调度器 |
| Scheduler claim 暂时失败使 worker 永久退出 | 对 I/O 和声明可重试的故障进行 0.1 至 5 秒指数退避；不做忙轮询 |
| Scheduler 不可恢复失败使等待者永久挂起 | 明确失败尚未执行的请求，并拒绝后续提交；其他 worker 已接管的运行可正常结束 |
| 恢复记录上下文损坏或孤立工作释放失败导致 worker 退出 | 拒绝损坏恢复输入；释放失败记录日志，由租约到期处理，保留 worker 服务能力 |
| Job 保留清理反复做列表删除与对象比较 | 排序后单次遍历决定淘汰项，避免二次复杂度扫描 |

### Job 默认资源预算

这些参数可通过 `sage.job.ephemeral` 的插件配置或 `InMemoryJobRuntime` 构造参数设置，并由 capabilities 暴露：

| 参数 | 默认值 | 含义 |
| --- | ---: | --- |
| `max_concurrent_jobs` | 32 | 同时执行的 Job |
| `max_admitted_jobs` | 1,024 | 排队、运行及尚未完成退出的任务总数 |
| `max_job_output_bytes` | 8 MiB | 单任务输出正文上限；任务请求可进一步降低 |
| `max_job_output_chunks` | 8,192 | 单任务输出块上限 |
| `max_buffered_output_bytes` | 256 MiB | 所有在运行及保留任务的输出正文总上限 |
| `max_buffered_output_chunks` | 65,536 | 所有在运行及保留任务的输出块总上限 |

达到输出上限后不再接纳超出的输出，任务仍继续执行并标记截断。历史输出淘汰后共享额度恢复。该预算限制的是框架保留的输出，不包括用户插件内部内存、Job payload、Session 原始账本和 Python 对象的全部开销。重连期内无法淘汰的终态记录可能触发新增任务背压；这是有意的行为变化。

第二轮联合回归为 **2,307 passed、20 skipped、6 warnings，37.49 秒**。随后补充“永久 claim 故障不影响其他已运行任务”的测试，独立执行本轮全部 **18 项故障与并发回归通过**。外部依赖跳过原因与下文一致。

第二轮修改后再次运行 100 会话、30 秒的内存并发持续测试：**1 passed，30.30 秒**。Ruff 与差异空白检查通过；短时测试的适用范围仍限于下文描述的内存工作负载。

## 本轮修复

| 路径 | 问题 | 修复与验证 |
| --- | --- | --- |
| 上下文固定区 | `developer` 消息可能进入历史裁剪或摘要 | 两种 reducer 均保留固定指令，增加参数化回归 |
| 持久摘要 | 已有摘要偏大时可能提前拒绝可通过压缩解决的请求 | 有新历史时允许合并压缩；固定指令及当前回合本身超限仍失败 |
| 流式提交 | 提交失败到定时器记录错误之间，排队生产者可能继续写入 | 在提交锁内记录失败，后续调用一致失败，不重试结果不明的提交 |
| 工具执行 | 读取运行控制信息失败时，已创建的工具任务无人接管 | 先读取控制信息，再创建任务；测试验证失败时工具未启动 |
| SQLite 会话记忆同步 | 每次读取整个会话的记录正文；同批重复 ID 可能使用过期快照 | 按主键读取目标记录；同批最后一次写入生效 |
| SQLite 会话记忆检索 | 全部命中加载并解码后才过滤、截断 | 在 SQL 中过滤后 LIMIT，仅解码返回记录；临时表支持大量边界 ID |
| 两个 SQLite 记忆插件 | 连接上下文只结束事务，连接依赖垃圾回收关闭 | 显式关闭连接，保留提交与回滚；测试覆盖成功与失败释放 |
| 文件记忆检索 | 一次性获取全部命中 | 游标迭代，取得足够符合范围的结果后停止 |
| Session Memory | 运行边界可能被用于不同会话；来源元数据变化被摘要缓存忽略 | 检查会话匹配；摘要覆盖完整记录，来源更新可同步 |
| 长驻进程缓存 | 单会话记录摘要、历史启动锁持续增长 | 单会话摘要缓存限制 4,096 项，空闲启动锁弱引用回收；不删除历史记录和幂等状态 |

此前本工作区已经实现的 System、保护区、压缩区预算、线性历史裁剪、技能读取缓存及共享后台任务限额，见[上下文预算与并发准备](sagents-v2-context-budget.md)。本轮回归同时覆盖这些变更。

## 验证

运行以下联合测试；原生沙箱测试需要支持对应操作系统沙箱能力：

```bash
python -m pytest -q tests/sagents/v2 tests/app/desktop_v2 tests/app/server_v2 --tb=line -rs
```

新增关键回归位于 `tests/sagents/v2/test_runtime_efficiency_audit.py`、`test_context_efficiency.py` 和 `test_ephemeral_session_store_matrix.py`，覆盖连接关闭与事务回滚、并发失败传播、跨会话边界、缓存淘汰、来源更新、幂等启动及固定指令保留。修改文件同时执行 Ruff 和 `git diff --check`。

最终联合结果：**2,290 passed、20 skipped、6 warnings，37.54 秒**。跳过项包括真实模型、MySQL / PostgreSQL、Linux cgroup / XFS 专用环境及默认关闭的并发持续测试；其中 PostgreSQL 插件可用性测试缺少 `asyncpg`。警告来自 Desktop 测试间接导入的 V1 Pydantic 弃用接口。

随后单独启用 `SAGE_V2_SOAK_SECONDS=30` 运行 `test_single_process_soak.py`：**1 passed，30.35 秒**。100 个并发会话的事件顺序、终态、CPU 占用断言及后台作业 / 沙箱保留上限通过。该测试使用内存实现且回合间有等待，属于短时并发回归，不是满载吞吐或长期稳定性证明。

本地 SQLite 检索基准：2,000 条记录，每条正文重复 `canary deployment` 50 次；允许三个记录 ID，返回两条，重复五次取中位数。以 `3ec3f7fa` 的插件实现为基线，结果 ID 均为 `r2`、`r1`：

| 实现 | 检索耗时中位数 |
| --- | ---: |
| 修改前 | 7.235 ms |
| 修改后 | 2.409 ms |

该结果只衡量上述本地检索场景，不包含模型、网络或真实多租户负载。过滤表的构建仍随传入 ID 数量增长，FTS 匹配与排序仍取决于索引规模；本轮没有将 SQLite 改造成分布式搜索服务。

## 服务器部署边界

- 已检查订阅队列上限与溢出处理、后台作业并发和保留限制、提交协调及取消处理。容量仍需要由部署的 Scheduler 配额、连接池、租户限额和存储插件共同约束。
- 内置 SQL Session Store 的单进程写入边界保持不变。多进程或多主机运行需要适合该部署的准入、调度及持久化插件，不能仅靠增加 worker 数保证正确性。
- SQLite 插件保留实例级操作串行化；长历史 FTS 更新、文件 Session 状态复制仍可能随数据量增长。本轮消除了无必要的全量正文加载，没有承诺全部存储操作固定耗时。
- Application / 模型客户端应按生命周期复用。动态构建客户端、实际供应商限流及连接耗尽需要在真实服务负载中观测。
- 生产验收应覆盖目标数据库、多租户和长会话，同时观测 P95/P99 延迟、事件循环延迟、RSS、文件描述符、队列深度，以及取消与断连后的任务数。未配置的真实外部服务测试不计作通过。
