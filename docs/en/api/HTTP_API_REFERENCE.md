# Server HTTP API

This page describes **`app/v2/server`**, not the legacy server. Open the running server's `/docs` or `/openapi.json` for request schemas, response models, and status codes.

## Authentication

`POST /api/auth/login` accepts JSON `username` and `password`. It returns `data.access_token` and sets the `sage_server_v2` cookie. Protected routes accept the authenticated identity through the server's dependency layer. Admin routes require an administrator.

## A2A and API keys

`/api/keys` manages Agent-bound machine credentials; keep the returned secret securely. Inbound `/a2a/v1` and the Agent Card routes require the `a2a` extra (included in `server`) and a Bearer API Key, not a user JWT. Cards and task reads require `a2a:read`; sending and cancellation require `a2a:invoke`. Cards are authenticated because one origin serves multiple users. Manage outbound peers through `/api/a2a-agents`; outbound calls do not require the inbound SDK extra.

## Chat and replay

`POST /api/agent` accepts AG-UI `RunAgentInput` and returns `text/event-stream`. Specify the Agent for a new conversation through `forwardedProps.agentId`; the first Run binds the Agent to the thread. Send `Last-Event-ID` when reconnecting to an accepted Run. Replay comes from canonical Session events; it is not stored in Redis.

`session_id` is the canonical Session identity: supplied IDs are preserved exactly; omitted IDs are generated by Sage. `threadId` is a compatibility alias and must equal `session_id` when both are provided. SSE lifecycle frames and result responses return the final `session_id`. Reuse it for follow-up requests. Ownership binds the tenant, Agent and Session; a global ID claimed by a different owner is rejected. Existing hashed Sessions remain accessible through the legacy mapping and return their persisted ID.

```json
{
  "session_id": "example-thread",
  "threadId": "example-thread",
  "runId": "example-run",
  "state": {},
  "messages": [{"id": "message-1", "role": "user", "content": "Hello"}],
  "tools": [],
  "context": [],
  "forwardedProps": {"agentId": "your-agent-id"}
}
```

Replace IDs appropriately. A new logical request needs a new Run ID; reconnection must not create another logical task.

The agent list uses `GET /api/agents/summary` for the current user. Admins use `GET /api/admin/agents` to retrieve all owners in one request. Summaries contain `id`, `name`, `description`, `model_id`, `model_name`, `tool_count`, and `skill_count`; admin summaries also contain `user_id` and `username`. Fetch the agent detail endpoint for full configuration.

## External runs and workspaces

External routes require a target-bound `Authorization: Bearer <API Key>` and a `SAGE-TENANT-ID` header. Reads require `a2a:read`, writes/execution require `a2a:invoke`, and interaction replies require `a2a:approve`. The server verifies the key binding, ownership, and grants; tenant, Session, and Run IDs are not credentials.

`PUT /api/agents/{agent_id}/workspace/files` imports `{directory, files}` with base64 file contents. It creates missing files only, accepts identical content again, and returns 409 on conflicts. Limits are 256 files, 4 MiB per file, and 16 MiB total. DELETE on the same route checks paths and workspace idleness.

`POST /api/agents/{agent_id}/runs?workspace_path=...` accepts AG-UI input and optional `runtimeContext` for this Run without modifying shared configuration. Reads, replies, cancellation, and downloads identify the exact `thread_id` and `run_id` and check ownership; replies also require the expected interaction ID and revision.

File downloads snapshot the Run-bound working directory, limited to 32 MiB and 512 entries. A directory superseded by a newer Run in the same Session returns 409; changes during packaging may return 503. Callers validate artifacts and Run identity. Sage does not interpret downstream business manifests or build customer projects.

## Guidance and Skills sync

The ZIP-upload mode of `PUT /api/agents/{agent_id}/guidance` uses multipart `prompt` and `files`, accepts 1–32 complete Skill ZIPs, and validates/reports each item. This upload branch does not require a user identity and must be exposed only to trusted callers; do not confuse it with Bearer Key-protected external Run routes.

`sync_bound=true` synchronizes existing bindings, requires the authenticated configuration owner, and cannot include prompt or ZIP uploads. Sync preserves models, tools, and execution policy; consult the HTTP schema and host implementation for configuration/resource activation behavior.

### Tool directory details

Each `GET /api/tools` entry includes `description`, `input_schema`, `side_effect_level`, and `requires_approval` alongside `name`, `category`, `source`, `default`, and `approval_key`. These fields project the currently discoverable `ToolDefinition` for read-only browsing; listing tools never invokes them. `default` identifies the initial tool set for new Agents. Tool approval declarations do not replace the Agent's current grants or execution policy.
