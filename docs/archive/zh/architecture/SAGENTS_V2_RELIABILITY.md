# SAgents V2：单机并发与 Agent 定制可用性

核对日期：2026-09-13。基线：`657c5c85` 与当前未提交的 V2 改动。
本文记录 SAgents V2 的可靠性核对；当前还包含 Desktop V2 自动保存与设置加载修复，详见桌面检查记录。旧 Desktop 未修改。

## 结论与适用范围

SAgents V2 已具备单机、单进程内多任务运行所需的核心机制，也有持久化、隔离、幂等和恢复测试支持。
Agent 创建并调用其他 Agent 的基础链路可以使用，但必须由宿主显式提供模型、工具、插件、技能与授权。
不能把这两个结论扩大成“任意配置都支持”“整个进程已统一限制资源”或“所有实现都高效”。

| 能力 | 当前证据与边界 |
| --- | --- |
| 创建、版本化、分叉、激活与调用 Agent | 已有模型工具调用和持久化测试；版本不可原地覆盖 |
| 多轮 Session 与问题回复 | 可续接同一版本；回复必须携带 `status.interaction.interaction_id`，避免旧回复落到新问题 |
| 创建出的 Agent 再创建 Agent | 已验证；每层必须显式获得管理工具权限 |
| 标准插件与 Flow 节点 | 可配置、调用宿主已注册的实现；具名 provider 选择经过多 offer 回归 |
| 插件源码自动落地运行 | 尚未实现自动构建、安装和隔离验证；包内源码文件不会自动执行 |
| 单机并发 | 验证了独立任务同时运行、重复 admission 去重、上下文隔离与初始化取消回收 |
| 并发总量控制 | 默认 Dispatcher 每个实例总上限 8、每租户 2；不同 Application 的上限不是整个宿主进程的统一总预算 |
| 任意 Agent 设置 | 受 manifest 和 Builder 能力限制；自定义 loop、Run scope Flow 插件节点等仍需宿主专用 driver |
| 单机多进程 / 分布式 | 本次 Agent Management 不承诺多宿主同时驱动同一运行目录；SQLite 库存事务不等于执行层分布式调度 |

## 本轮发现与修复

1. **资源文本被改变**：通用 StrictModel 会裁掉字符串首尾空白，影响包内文件和提示词。改用 VerbatimText，覆盖 SQLite 往返、manifest 解析和 AgentDescriptor，保留源码与指令原文。
2. **授权期间配置可被修改**：模型的 frozen 不会冻结内部 dict。保存/验证入口现在先复制并重新校验完整快照，后续调用者修改原始字典不会改变已接收的包。
3. **关闭打断已接收的保存操作**：save 内再次进入公开 validate 的关闭检查，会在服务开始关闭后拒绝已经接收的保存。改为在同一个操作生命周期内调用内部验证，再等待其完成后关闭。
4. **回复重试可能误答新问题**：旧接口仅按任务寻找“当前问题”。现在要求明确问题 ID，持久化回复命令，使用 Native 幂等解析；已接受回复在恢复前中断，可在重启后重试。并发重复提交不会回答下一轮问题。
5. **具名插件配置未真正生效**：继 Flow 节点后，工具 catalog/executor 和通用能力装配也按指定 offer 名称选择；多个 executor 不再任取第一个。隐式 default 的单 provider 保持兼容，歧义明确报错。
6. **状态查询争用 SQLite 写锁**：只读 invocation 查询不再执行 BEGIN IMMEDIATE。回归测试持有 reserved writer lock 时仍能读取状态。

上一轮已修复不同 Agent 初始化被全局锁串行阻塞的问题，并确保同一实例的并发初始化只进行一次。

## 并发验证

`test_concurrent_managed_runs_are_isolated_and_duplicate_admission_is_once` 使用真实 Builder、Session 存储、Dispatcher 与管理服务，模型为带 20ms 异步等待的脚本模型。

- 同时提交 24 个不同任务，加上同一任务的 8 次重复提交。
- 产生 24 个不同 Run 和 Session，只有 24 次模型调用，全部完成。
- 每个模型请求只包含自身任务标记，未混入其他任务。
- 单独运行该测试时耗时约 0.759 秒，模型调用并发峰值为 2，与该租户的默认限制一致。
- 另有回复持久化后中断、服务重启、8 次并发重复回复、下一轮问题不被旧答案覆盖的测试。

这是一组可复现的并发正确性场景；耗时包含本地存储与轮询，不能当作模型吞吐、生产 SLA 或框架极限。
测试文件：`tests/sagents/v2/test_agent_management_matrix.py`。

## 仍需做的可靠性与效率工作

1. **宿主总预算**：统一所有 managed Application 的执行、模型连接、工具子进程和递归任务总量。当前独立 Dispatcher 的并发上限不能直接当作全进程上限。
2. **空闲实例回收**：服务默认最多缓存 32 个 Application，无空闲淘汰。需要根据活跃 Run、待回复交互和资源引用安全回收，避免长期版本迭代耗尽容量。
3. **冷启动成本**：新版本和显式 validate 仍构建全部 Agent，Flow 还可能初始化不可达成员。同一已保存版本的重试现在免重复装配；后续还可按可达范围装配，但跨宿主配置缓存必须包含绑定版本。
4. **长时间负载验证**：还需真实模型、慢/失败插件、长会话、多小时运行、内存趋势与 P95/P99 延迟基准。当前用例通过不能替代这些验证。
5. **故障注入范围**：已验证部分重启与幂等边界；仍需系统覆盖磁盘写满、进程强杀、插件关闭失败、网络中断及资源限额。

这些工作都属于框架运行与工程可靠性，不需要引入监督学习闭环。

## 追加优化：初始化压力与重复保存

- `AgentManagementService(max_concurrent_builds=4)` 对同一服务内所有验证和运行实例初始化共享并发名额，宿主可调整。验证会一直持有名额直到临时 Application 关闭。它限制初始化峰值，不替代运行期资源预算，也不代表全进程其他服务受到限制。
- 同一用户、package ID/version 的保存使用可回收的局部锁；12 次并发相同保存只装配一次。不同版本、不同用户仍可并行，且都受初始化上限约束。SQLite 保留最终跨连接唯一性检查。
- 已保存的相同 ref 返回 `reused: true`，仍执行当前 save/validate 授权检查，不再次初始化插件。`validate` 始终重新探测当前宿主能力；复用保存结果不构成新的可运行性证明。
- 已存在的冲突版本在插件初始化前拒绝，避免明知不能保存仍构建模型与插件。
- 取消等待中的验证可直接退出；已进入初始化的验证会先完成其构建与关闭，再删除临时目录、释放名额和响应取消。因此慢插件会延长取消等待时间，换取有序清理。
- Session 归属查询新增 `(owner, ref, agent, session_id)` SQLite 表达式索引；测试验证句柄写入后归属正确，查询计划实际使用该索引。
- 包内容哈希与序列化在取得 SQLite 写锁之前计算，且每次写入复用一次结果，减少大包重复序列化和持锁时间。

专项测试现为 33 项，覆盖重复保存、冲突提前拒绝、验证与运行共享限额、取消与关闭及索引使用。空闲实例自动淘汰仍未实现，缓存上限仍由 `max_applications` 控制。

回复重试追加了真实 revision conflict 回归：旧命令因版本过期未获接受时，下次相同答案可基于新版本重试；条件删除保证不移除其他并发请求已经更新的命令。当前 V2 核心回归为 2092 项通过（原生沙箱排除范围不变）。

## 追加：设置事务与失败清理

验证实例关闭失败时，管理服务保留 Application 与临时目录，后续 close 可重试。服务关闭或验证清理失败后保持 draining，拒绝新管理操作；清理失败不会恢复运行准入。新增两项故障注入回归，专项共 33 项。

Desktop V2 使用串行字段 PATCH 与单服务事务锁保护设置，关闭前提交工作区、预览与沙箱输入；Agent 失败回滚使用已确认快照。sidecar revision 为 6。后端 168 项、Flutter 202 项、核心 2092 项通过；原生沙箱排除范围不变。实现和剩余边界见 [整体审查](V2_COMPREHENSIVE_REVIEW.md)。

## 追加：运行时资源管理

已新增可选资源发现及严格准入、共享模型调用额度、显式空闲实例回收、Flow 可达成员装配。Desktop V2 的运行模型已共享额度。接入方式、测试与尚未覆盖的预算和产品流程详见 [运行时资源管理](../../../zh/architecture/SAGENTS_V2_RESOURCE_MANAGEMENT.md)。此前“没有回收”“全局模型额度待实现”等描述的当前状态以此文档为准；自动回收和全部资源的统一预算仍未实现。

## 追加：容量回收与历史读取

管理操作现在持有实例使用计数；缓存满时默认回收 300 秒未使用、可持久恢复且无非终态 Run 的实例。`auto_release_idle_seconds=None` 可关闭自动回收。终态结果在查询、回收前及正常关闭前归档，已归档查询无需重新构建 Application，且仍检查当前读取授权。崩溃前尚未归档的记录仍走恢复装配路径。当前机制替代此前“自动回收尚未实现”的描述，详见 [运行时资源管理](../../../zh/architecture/SAGENTS_V2_RESOURCE_MANAGEMENT.md)。
